# 004 Миграция некоторых коллекций на Cassandra

## Описание

Во время «чёрной пятницы» интернет-магазин использовал MongoDB с шардированием на основе диапазонов (Range-Based Sharding). При резком увеличении нагрузки (50 000 запросов/сек.) возникла высокая задержка при масштабировании:
При добавлении новых шардов MongoDB полностью перераспределяла данные между всеми узлами, что вызывало просадку latency в пик нагрузки, так как система тратила ресурсы на перемещение данных.
Руководство решило перейти на БД Cassandra, чтобы обеспечить:

- Высокую отказоустойчивость (leaderless‑репликация).
- Быстрое горизонтальное масштабирование без полного перераспределения данных.
- Равномерное распределение данных.

Нужно определить, какие коллекции и операции будут мигрированы на Cassandra, а какие останутся в MongoDB, учитывая требования к консистентности и производительности. Также нужно определить partition key и cluster key для каждой коллекции, которая будет мигрирована на Cassandra. И стратетегию обеспечения целостности данных.

## Решение

### Коллекция и требования к консистентности

| Коллекция | Критичность | Требования                             | Casandra? | Обоснование                                                                                                                                                                                                                                                                         |
| --------- | ----------- | -------------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| orders    | Высокая     | Строгая консистентность                | Да        | История заказов и статус заказа требуют строгой консистентности, так как пользователи ожидают немедленного отображения статуса заказа. Cassandra обеспечивает высокую доступность и масштабируемость, что важно для обработки большого объема заказов.                              |
| products  | Высокая     | Строгая консистентность, сложные связи | Нет       | Информация о товаре и категориях требует сложных связей и агрегаций, которые лучше обрабатываются MongoDB. Кроме того, данные о товарах обновляются не так часто, что позволяет использовать MongoDB для хранения этой информации.                                                  |
| carts     | Высокая     | очень частые записи/чтения             | Да        | Содержимое корзины требует высокой производительности при записи и чтении, так как пользователи часто добавляют и удаляют товары из корзины. Cassandra обеспечивает высокую производительность при работе с большим объемом данных и поддерживает быстрые операции записи и чтения. |

### Дизайн таблиц Cassandra

#### 1. Таблица `orders`

**Паттерны доступа:**

- Получение заказа по ID
- Получение истории заказов пользователя (отсортированных по дате)
- Получение заказов по статусу для пользователя

**Partition Key:** `user_id` — обеспечивает равномерное распределение данных по узлам, так как запросы чаще всего идут в контексте конкретного пользователя.

**Clustering Key:** `created_at DESC, order_id` — позволяет получать заказы в хронологическом порядке (новые первыми) и гарантирует уникальность записей.

**Стратегия консистентности:**

- `QUORUM` для записи и чтения — обеспечивает строгую консистентность при сохранении высокой доступности.
- Replication Factor = 3

#### 2. Таблица `carts`

**Паттерны доступа:**

- Получение корзины по ID пользователя
- Добавление/удаление товара из корзины
- Обновление количества товара

**Partition Key:** `user_id` — каждый пользователь имеет одну корзину, что обеспечивает естественное распределение нагрузки.

**Clustering Key:** `product_id` — позволяет эффективно управлять товарами в корзине (добавление, удаление, обновление количества).

**Стратегия консистентности:**

- `ONE` для записи, `ONE` для чтения — максимальная производительность, eventual consistency приемлема для корзины.
- Replication Factor = 3
- Использование LWT (Lightweight Transactions) только для критичных операций (например, резервирование товара при оформлении заказа).

### Стратегия обеспечения целостности данных

#### 1. Механизмы Cassandra для обеспечения консистентности

Cassandra предоставляет три основных механизма для обеспечения согласованности данных между репликами:

- **Hinted Handoff** — временное хранение записей для недоступных узлов с последующей передачей при восстановлении.
- **Read Repair** — синхронизация реплик при обнаружении расхождений во время чтения.
- **Anti-Entropy (nodetool repair)** — фоновая синхронизация всех реплик для устранения расхождений.

#### 2. Выбор механизмов для коллекций

##### Таблица `orders`

**Требования:** Строгая консистентность, критичные данные, недопустимы потери.

| Механизм       | Использование | Настройка                                                                              | Обоснование                                                                                                                                      |
| -------------- | ------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hinted Handoff | Включен       | `hinted_handoff_enabled: true`<br>`max_hint_window_in_ms: 10800000` (3 часа)           | Обеспечивает доставку записей на временно недоступные узлы. 3 часа достаточно для большинства сценариев восстановления.                          |
| Read Repair    | Включен       | `read_repair_chance: 0.1`<br>`dclocal_read_repair_chance: 0.2`                         | Фоновая синхронизация при 10% чтений (глобально) и 20% (локально в DC). Баланс между консистентностью и производительностью.                     |
| Anti-Entropy   | Еженедельно   | `nodetool repair -pr ecommerce orders`<br>Запуск через cron каждое воскресенье в 03:00 | Регулярная полная синхронизация для устранения накопленных расхождений. Еженедельный интервал достаточен при использовании QUORUM + Read Repair. |
| Consistency    | QUORUM/QUORUM | Write: `ConsistencyLevel.QUORUM`<br>Read: `ConsistencyLevel.QUORUM`                    | Гарантирует строгую консистентность: при RF=3 запись/чтение подтверждается 2 узлами. Защита от чтения устаревших данных.                         |

##### Таблица `carts`

**Требования:** Высокая производительность, eventual consistency приемлема, частые операции записи/чтения.

| Механизм       | Использование | Настройка                                                                    | Обоснование                                                                                                                                                      |
| -------------- | ------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hinted Handoff | Включен       | `hinted_handoff_enabled: true`<br>`max_hint_window_in_ms: 3600000` (1 час)   | Более короткое окно (1 час), так как данные корзины имеют TTL 30 дней и eventual consistency приемлема. Снижает нагрузку на хранение hints.                      |
| Read Repair    | Частично      | `read_repair_chance: 0`<br>`dclocal_read_repair_chance: 0.05`                | Минимальный Read Repair (5% локально) для снижения latency при чтении. Eventual consistency достаточна для корзины, конфликты разрешаются через last-write-wins. |
| Anti-Entropy   | Ежемесячно    | `nodetool repair -pr ecommerce carts`<br>Запуск первого числа каждого месяца | Редкие полные синхронизации, так как данные имеют TTL и eventual consistency приемлема. Достаточно для устранения tombstones и обеспечения gc_grace_seconds.     |
| Consistency    | ONE/ONE       | Write: `ConsistencyLevel.ONE`<br>Read: `ConsistencyLevel.ONE`                | Максимальная производительность. Eventual consistency с разрешением конфликтов через timestamps (last-write-wins). Допустимо для корзины покупателя.             |

#### 3. Денормализация данных

- В таблице `orders` дублируются основные данные о товарах (название, цена на момент заказа).
- В таблице `carts` хранятся только `product_id` и количество, актуальные данные о товаре запрашиваются из MongoDB при отображении.

#### 4. Обработка конфликтов

- **Orders:** Использование `QUORUM` обеспечивает строгую консистентность, конфликты исключены.
- **Carts:** Eventual consistency с использованием timestamps для разрешения конфликтов (last-write-wins). При одновременном изменении корзины с разных устройств побеждает последняя запись.

#### 5. Синхронизация между системами

- При создании заказа данные записываются в Cassandra (`orders`) с дублированием критичной информации о товарах из MongoDB.
- Использование паттерна Saga для распределенных транзакций (создание заказа → резервирование товара → очистка корзины).
- Event sourcing для критичных операций с возможностью воспроизведения истории изменений.

#### 6. Резервное копирование

- Ежедневные snapshot'ы таблиц Cassandra.
- Point-in-time recovery для критичных операций.

#### 7. Настройка автоматического repair

```bash
# Создание cron-задач для автоматического repair

# Repair для orders - каждое воскресенье в 03:00
0 3 * * 0 /usr/bin/nodetool repair -pr ecommerce orders >> /var/log/cassandra/repair-orders.log 2>&1

# Repair для carts - первое число каждого месяца в 04:00
0 4 1 * * /usr/bin/nodetool repair -pr ecommerce carts >> /var/log/cassandra/repair-carts.log 2>&1
```

### Инструкции по созданию таблиц в Cassandra

#### Создание keyspace

```cql
CREATE KEYSPACE IF NOT EXISTS ecommerce
WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'datacenter1': 3,
    'datacenter2': 3
}
AND durable_writes = true;
```

#### Таблица orders

```cql
CREATE TABLE IF NOT EXISTS ecommerce.orders (
    user_id UUID,
    created_at TIMESTAMP,
    order_id UUID,
    status TEXT,
    total_amount DECIMAL,
    currency TEXT,
    items LIST<FROZEN<order_item>>,
    shipping_address FROZEN<address>,
    billing_address FROZEN<address>,
    payment_method TEXT,
    updated_at TIMESTAMP,
    PRIMARY KEY (user_id, created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);

-- Определение UDT для элементов заказа
CREATE TYPE IF NOT EXISTS ecommerce.order_item (
    product_id UUID,
    product_name TEXT,
    quantity INT,
    price DECIMAL,
    discount DECIMAL
);

-- Определение UDT для адреса
CREATE TYPE IF NOT EXISTS ecommerce.address (
    street TEXT,
    city TEXT,
    state TEXT,
    zip_code TEXT,
    country TEXT
);

```

#### Таблица carts

```cql
CREATE TABLE IF NOT EXISTS ecommerce.carts (
    user_id UUID,
    product_id UUID,
    quantity INT,
    added_at TIMESTAMP,
    updated_at TIMESTAMP,
    PRIMARY KEY (user_id, product_id)
);
-- Индекс для быстрого получения всех товаров в корзине
CREATE INDEX IF NOT EXISTS ON ecommerce.carts (added_at);
```

## Преимущества решения

1. **Высокая производительность:** Cassandra обеспечивает линейное масштабирование при добавлении новых узлов без полного перераспределения данных.
2. **Отказоустойчивость:** Leaderless-репликация исключает единую точку отказа.
3. **Гибкая консистентность:** Возможность настройки уровня консистентности для каждой операции в зависимости от требований.
4. **Оптимальное распределение нагрузки:** Partition key по `user_id` обеспечивает равномерное распределение данных.

## Недостатки и риски

1. **Сложность миграции:** Требуется переписать логику доступа к данным и провести миграцию существующих данных.
2. **Денормализация:** Необходимость дублирования данных увеличивает объем хранилища.
3. **Ограниченная поддержка транзакций:** Отсутствие ACID-транзакций требует реализации паттерна Saga.
4. **Eventual consistency для корзин:** Возможны временные расхождения данных между репликами.
